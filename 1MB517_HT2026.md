# PART 0 - Knowing your way around & using Plink   	    

[PLINK](https://www.cog-genomics.org/plink2) is a software for fast and efficient filtering, merging, editing of large SNP datasets, and exporting to different outputs directly usable in other programs. It can store huge datasets in compact binary format from which it reads data very quickly.

```ruby

```

This is what a basic command structure looks like in `PLINK`: 

```ruby
plink --file_type_flag {INPUT_FILE} --command_flag {COMMAND_SPECIFICATION} --output_file_command --out {OUTPUT_FILE}
```

For example, to do filtering of missing markers at a cutoff of 10% missingness:

```ruby
plink --bfile INPUT_FILE --geno 0.1 --recode --out OUTPUT_FILE
```

*What is the command above doing?* Reading in a bed format file (`--bfile`) called 'file1', doing the filtering (`--geno 0.1`), converting it to ped format file (`--recode`) and giving it to you (`--out`) as a file called 'file2'.


## PLINK file formats

A single data set that we could have had in a single VCF file is coded into two or three different files in the `PLINK` format. At least two files are used, one containing information about the 'family' (the samples in your data set), and one or two more files containing information about the genotypes (the alleles that each individual has, and information about those sites in the genome). These are the three 'styles' in which we can have `PLINK` files:

**ped format**: usual format (.ped and .fam)

- `.ped` - marker info
- `.fam` - sample and genotype info

**bed format**: binary/compact ped format (.fam, .bim and .bed)

- `.fam` - sample info 
- `.bim` - marker info  
- `.bed` - genotype info (binary format)

**tped format**: transposed ped format (.tfam and .tped)

- `.tfam` - sample info
- `.tped` - marker and genotype info in transposed format

## Step 4 - Filtering for SNPs out of HWE

SNPs that are not in Hardy-Weinberg equilibrium (HWE) usually indicate problems with the genotyping/sequencing. However, to avoid filtering out SNPs that are selected for/against in certain groups (especially when working with case/control data) filtering HWE *within groups* is recommended. Now, we will just filter the entire data set for SNPs that aren’t in HWE with a significance threshold of 0.001. Again, in real research, this filter is better applied when all data has been merged.

```ruby
plink --bfile INPUT_DATASET --hwe 0.001 --make-bed --out OUTPUT_DATASET
```

*How many SNPs were excluded?*  

If you want to look at the results from the HWE test, you can use the command below. By running it, you can also obtain the observed and expected heterozygosities at each site:

```ruby

```

Look at file 'OUTPUT_DATASET_hwe.hwe' (with `head` or `less`), do you understand the output?

The output file has the following format:

- `SNP`: SNP identifier
- `TEST`: Code indicating sample
- `A1`: Minor allele code
- `A2`: Major allele code

There are additional filtering steps that you can do. `PLINK` website lists all the cool commands that you can use to treat your data. Usually, we also filter for related individuals and do a sex-check on the X-chromosome to check for sample mix-ups. 


## Step 5 - Filtering out related individuals (just the Modern Reference dataset)

## Step 7 - Plot a PCA using the modern reference individuals

Plot a PCA using `PLINK` on the modern reference individuals and describe what you see.

```plink --bfile INPUT_DATASET --pca --out OUTPUT_DATASET```

The PCA analysis should give you an '.eigenvec' and an '.eigenval' file as outputs. In the `.eigenvec` file is the main output for the number of principal components that you specified (default of 20). The first and second column specify the family (population) and individual (sample) names for each of your samples. The res of the columns contain the eigenvectors from each of the 20 computed principal components. The `.eigenval` lists the 20 eigenvalues, which describe the proportion of variance each of the principal components is summarizing. To work out the percentage of variation each PC explains, you divide your particular PC eigenvalue by the sum over all the eigenvalues. 

Suggestion on how to plot the PCA (make sure to change 'YOUR_DATASET.eigenvec'):

## Step 8 - Before merging, let's unify SNP names 

When merging datasets from different genotyping chips, the same position/variant can have different names on different chips. The following code can be used on the `.bim` files to change the SNP name into the names based on position (chr_position). It also does a few other things. Can you understand why? Run the code below for both reference datasets and your unknown dataset. Check the `.bim` files before and after making the change to see what happened with the SNP names.

```ruby
# Choose the dataset that you are editing at the moment
DB=YOUR_DATASET

# Change SNP names in .bim file
cp ${DB}.bim ${DB}.bim_original; cut -f1,4 ${DB}.bim > list_snp.txt; sed -i 's/\t/_/g' list_snp.txt; awk 'NR==FNR{a[NR]=$0;next}{$2=a[FNR]}1' list_snp.txt ${DB}.bim_original > ${DB}.bim; sed -i 's/ /\t/g' ${DB}.bim

# Write duplicated SNPs in duplicated_SNPs.txt
# This is better than using "dupvar" option in PLINK, because triplicated/fourplicated/etc SNPs are also selected
cut -f 2 ${DB}.bim | sort | uniq -d > duplicated_SNPs.txt; wc -l duplicated_SNPs.txt

# Remove duplicated SNPs from dataset 
plink --bfile ${DB} --exclude duplicated_SNPs.txt --make-bed --out ${DB}_noDupSNPs

# Write down Indels to indel_SNPs.txt
grep D ${DB}_noDupSNPs.bim > indel_SNPs.txt

# Remove Indels from dataset
plink --bfile ${DB}_noDupSNPs --exclude indel_SNPs.txt --make-bed --out ${DB}_noDupSNPs_noIndels
```

## Step 1 - LD Pruning 

Before running PCA & ADMIXTURE it is advisable to prune the data to thin the marker set for linkage disequilibrium.

Why LD Pruning is Important:
- **Reducing redundancy, and increasing efficiency**:
     * Linked SNPs: SNPs that are in linkage disequilibrium (LD) are not independent of each other, meaning that their allele frequencies are correlated due to physical proximity on the chromosome or other forces such as natural selection. 
     * Pruning: By removing SNPs in high LD, you reduce redundancy in your dataset, which helps ensure that the remaining SNPs are more independent. You will never reach full independence though, so there is some compromise that needs to be done.
     * Smaller data set: Pruning reduces the number of SNPs, making the dataset smaller and more manageable. This can lead to faster computation times and reduced memory usage, especially in computationally intensive analyses.
- **Statistical soundness**:
     * PCA and ADMIXTURE: Analyses like Principal Component Analysis (PCA) and ADMIXTURE can be skewed by linked SNPs because these methods assume independence between markers. LD pruning helps avoid bias and overestimation of population structure or admixture components.
     * Avoiding overfitting: Pruning helps prevent overfitting in models by removing highly correlated variables (SNPs).

You can read up on how to prune for LD (<https://dalexander.github.io/admixture/admixture-manual.pdf>).

For example, using `--indep-pairwise 50 10 0.5` on `PLINK` specifies:

- Window Size (50): This means `PLINK` will examine LD between SNPs within a sliding window of 50 SNPs. A smaller window size would prune less aggressively, but a window of 50 SNPs is generally considered a good balance between capturing local LD and not being too strict.
- Step Size (10): The window will slide across the genome in steps of 10 SNPs. This step size allows for a reasonable balance between computational efficiency and thoroughness in detecting SNP pairs in high LD.
- r² Threshold (0.5): SNP pairs with an r² greater than 0.5 within the window will have one SNP removed. An r² of 0.5 is a moderate threshold that ensures SNPs in very high LD (strongly correlated) are pruned, while keeping more SNPs that are only moderately correlated.

## Step 4 - ADMIXTURE 

`ADMIXTURE` is a clustering software that we use with the aim to infer population and individual ancestries. It is nevertheless a clustering algorithm, which only describes the data at hand, like PCA, and does not test any specific hypothesis. In broad strokes, it splits the genome into smaller segments, and asks the question "Which ancestry does this segment of the genome match best?". The number of 'ancestries' we specify ourselves (e.g. 2, 3, 4, 5), and `ADMIXTURE` splits the genetic data into that many group, by maximizing within-group similarity (in terms of allele frequencies).

`ADMIXTURE` runs directly from `.bed` or `.ped` files and needs no extra parameters for file preparation. 

A basic `ADMIXTURE` run looks like this, where 'K' is the number of clusters you want to split the data into:

```ruby
admixture -s time {your_dataset}.bed K
```

We need to run many iterations at each K value, because there can be some stochasticity in the clustering process. Therefore, a compute cluster and some scripting are very useful.

First, we have to check what `ADMIXTURE` is called in Pelle:

```ruby
module spider ADMIXTURE
module load ADMIXTURE/1.3.0
```

Create a script file (using `nano`, for example: `nano run_admixture.sh`) and paste in the code below, which will run ADMIXTURE for five values of K (2 to 6) and 3 iterations at each K value.

```ruby
#!/bin/bash

# loop over K values
for kval in {2..6}; do

   # loop over the iterations
   for itir in {1..3}; do
           (echo '#!/bin/bash -l'
           echo "

           ## create a folder with the K value and iteration value
           mkdir ${kval}.${itir}

           ## move into this folder
           cd ${kval}.${itir}

           ## load and run ADMIXTURE for that specified K
           module load ADMIXTURE/1.3.0
           admixture -j3 -s $RANDOM $1 ${kval}

           ## move one folder up
           cd ../
           exit 0") |

           ## send all the previous code as an independent job
               sbatch -n 3 -t 72:00:00 -A uppmax2026-1-255 -J ADMX.${kval}.${itir} -o ADMX.${kval}.${itir}.output -e ADMX.${kval}.${itir}.message

       ## continue with the next iteration on the same K
       done

## continue with the following K
done
```

You can see a `$1` in the script. This is asking for an input file to be given to the `run_admixture.sh` script, which will be the *full directory* and *file name* of your data set. Sending the job can look like this:

```ruby
bash run_admixture.sh /proj/uppmax2026-1-255/.../.../YOUR_DATASET.bed
```

After a successful `ADMIXTURE` run, you should be seeing a bunch of new folders being created in the ADMX directory, as well as some 'output' and 'message' files. In each of the folders, you will find the output `.P` and `.Q` for each iteration. These are the files we're interested in, but the 'message' file should inform you about any errors in your script.

*If you decide to work on PONG locally, you need to edit each ```Q``` file by adding the right k & iteration number to each one. After doing this for all folders, you can move all the ```Q``` files to a directory of your liking.*
